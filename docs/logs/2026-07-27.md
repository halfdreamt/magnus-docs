Log:
- **Completed a source-level study of five external MTG modeling approaches.** Shallow local checkouts were pinned at Forge `fdc720c6`, XMage `2c43ec8c`, Magarena `efa0aba8`, Argentum Engine `89312eed`, and mtgish `3ea0be82`. The forgotten second engine was XMage.
  - Forge's card DSL demonstrates the value of separate operations for triggers, replacements, defined/remembered objects, costs/payers, zone visibility, duration, cleanup, choices, and AI hints. Difficult cards such as Doubling Season and Chains of Mephistopheles are compositional pipelines rather than monolithic special cases.
  - XMage's typed Java abilities/effects/targets/filters/watchers and scenario suite are strong primitive and test witnesses. Its own TODOs also demonstrate why a mature implementation is evidence rather than a rules authority.
  - Magarena's grammar plus Groovy escape hatch reaches an explicit ceiling: the inspected checkout had 14,988 playable scripts and 5,293 entries in `scripts_missing`. That visible missing ledger is safer than silently accepting partial parses.
  - Argentum independently converged on the recommended workflow: external mtgish IR feeds a capability bridge and conservative draft emitter; generated cards remain non-authoritative, stage outside runtime content, and require compilation/fidelity checks plus reviewed scenario tests.
  - mtgish is useful for clause taxonomy, trie/template parsing, and understanding pronoun/back-reference difficulty. Its README leaves licensing unresolved, so it remains research-only and must not be vendored.
- **Measured the available external evidence against a fresh Scryfall-backed MTGCLI universe.** The initial universe contained 31,676 black-border paper cards, 15,942 whole-card clause-covered cards, 15,734 gap cards, and 20,135 unmodeled clauses.
  - The read-only audit found Forge matches for 14,509 gap cards, XMage matches for 14,238, Forge/XMage agreement for 14,105, and XMage scenario-test references for 2,281. Magarena implemented 4,945 of 8,008 matched-or-explicitly-missing cards.
  - These are lower-bound joins and prioritization signals, not correctness or completeness claims. Filename matching can miss aliases and unusual multi-face registration, and agreement between engines never blesses MTGCLI IR.
  - High-evidence remaining families include kicker (184 cards / 181 Forge-XMage agreement), madness (59/57), echo (43/42), cumulative upkeep (42/42), mutate (34/34), ninjutsu (34/34), and plot (34/33).
- **Built the read-only `tools/external_engine_audit.py` implementation-witness pipeline in MTGCLI.** It consumes `coverage_universe_gaps.json`, extracts Forge DSL and XMage typed fingerprints, finds XMage scenario references, distinguishes Magarena implemented/missing scripts, records pinned revisions, clusters clause shapes, and emits per-card JSON dossiers plus a Markdown leaderboard. It never changes card IR, the modeling ledger, or coverage status.
  - The first full scan exceeded five minutes; candidate filename indexing reduced the same 15,734-card / 15,137-shape run to 36.9 seconds. Remaining alias/index limitations are explicitly tracked in `KNOWN_ISSUES.csv`.
  - Adapter fixture tests cover cross-engine joins, primitive extraction, Magarena missing status, test references, punctuation, and real ligature normalization.
- **Promoted one evidence-ranked family as a fidelity-gated POC.** The exact clause “This creature can block only creatures with flying” appeared as 26 gaps; twenty-one cards had no other gap. MTGCLI already had a runtime `block_only_flying` primitive for one hand-authored card, so an exact anchored template now compiles the shared Oracle form into that existing behavior.
  - The 21-card registered pool includes Cloud Sprite, Welkin Tern, Stormbound Geist, Shacklegeist, Vaporkin, and sixteen peers. Every item has an explicit compiled-IR assertion and is instantiated in combat against a ground attacker and a flyer. Separate negative controls prove reach is not flying and prove the restriction is on blocking rather than attacking.
  - Scoped coverage is L3: 21/21 covered, zero gaps, zero untracked clauses, zero open card-gap rows. The universe moved from 15,942 to 15,963 whole-card clause-covered cards and from 20,135 to 20,109 unmodeled clauses; the other five clause instances improved without becoming whole-card covered.
  - Verification passed the general effects suite, adapter suite, per-card behavioral suite, per-card audit dump, scoped coverage gate, and the repository's 172-file fast smoke gate.
- **Decision: proceed with a capability bridge and candidate pipeline, not a bulk importer.** External engines should rank repeated capability work, suggest MTGCLI primitive decompositions, and supply scenario intent. Oracle text and the Comprehensive Rules remain the specification; a model promotes only through registered pools, exact clause accounting, native behavior tests, and the existing landing gate.
  - Phase 1 is authoritative name/registration manifests and pinned revision drift.
  - Phase 2 is a calibrated external-fingerprint-to-MTGCLI bridge labeled `exact`, `test-hint`, or `unknown`, with non-executable draft/scaffold output and no partial-IR fallback.
  - Phase 3 works exact static/keyword lanes first, then treats kicker, madness, mutate, replacement chains, linked abilities, copy/layers, hidden information, and zone identity as dedicated engine units.
  - Phase 4 translates interaction intent into original MTGCLI tests and resolves cross-engine disagreements against the rules rather than majority vote.
- **Published the MTGCLI study and proof of concept.** Branch `work/engine-study-poc` is pinned at `5513611a9d3810fc188274e2e88774dbe8bca182`; primary feature commit `8ecfd4f` contains the report, adapter, pool, template, tests, changelog, reflection, and ledger updates, while `5513611` tightens the L3 evidence to runtime behavior per card. The detailed report is `docs/external-engine-modeling.md`. The unit awaits integration rather than racing a direct push to MTGCLI `main`.

The adapter remains versioned with MTGCLI because it consumes MTGCLI's gap schema and policy; the cross-project runner keeps reference repositories and generated dossiers outside runtime code.
