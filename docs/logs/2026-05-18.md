- Magnus3: Disciplined Starving / CurrentFamine A/B (the answer)
  - Added `constexpr bool kUseStarvingComponents` flag in `ConsumptionSystem.hpp`. When false, the Starving and CurrentFamine state moves into two process-level side maps (`unordered_map<entity_id, since_tick>`, `unordered_map<community_id, flecs::entity>`). All other behavior — interval bookkeeping, death rolls, famine lifecycle, BirthSystem's starving gate via the `starving_ids` set — identical.
  - **Side-map variant: 163ms sim (vs 397ms with components — 58% reduction). "flecs_overhead" 35ms (vs 218ms — 84% reduction). Tables 4,492 (vs 6,740 — 33% reduction).**
  - Per-subsystem callback timings barely move (consume 17.4→14.7ms, exogamy 35→27ms). Every minute is in the post-callback flush — that's exactly where Flecs applies queued component add/remove ops, and where archetype churn cost lives.
  - **Root cause confirmed:** the dominant cost of the rewrite is Flecs archetype churn from per-person `Starving` and per-community `CurrentFamine` component toggling. ~54k Starving moves + 2.2k CurrentFamine moves per 1000y → ~217ms of flush cost.
- Magnus3: Side-map variant produces slightly different outcomes (4,698 vs 4,728 events; community pops 20/23/28 vs 20/30/17 at Y1000)
  - Verified: each variant is deterministic across re-runs of itself.
  - Verified: no overlapping or back-to-back famine events in either path — both correctly maintain one continuous famine per spell. (Initial hypothesis "side-map prevents spurious re-opens" was wrong.)
  - Real cause of the delta is almost certainly Flecs iteration order: in the component path, communities with `CurrentFamine` sit in a different archetype table from those without, so `ecs.each<CommunityIdentity, FoodStores>` visits them in a different order than the side-map path (where all communities live in the same table). Different visit order → different assignment of `next_event_id` → divergent downstream RNG paths once anything keys off entity IDs. Both are equally valid simulations.
